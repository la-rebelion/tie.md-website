# Requirements traceability

The requirements traceability matrix (RTM) connects scoped requirements to the artifacts and evidence that support them. New to RTMs? Read [Requirements traceability](/docs/concepts/requirements-traceability) first.

tie.md stores its RTM in `.tie/rtm.yaml`, a versioned YAML file you commit with the project. Comments and unknown fields survive edits made through tie.md.

## The trace graph

A requirement may link forward to:

```text
requirement → design → task → code → test → defect/change request → release
```

The same relationships are navigable backward. A test can reveal which requirement it verifies; a changed code artifact can reveal which tests and requirements may be affected.

## Evidence states

tie.md keeps these states separate:

- **Pending:** no implementation evidence is linked.
- **Designed:** approved design evidence exists.
- **Built:** implementation evidence exists.
- **Tested:** a relevant test exists.
- **Passed:** current linked test evidence passes.
- **Delivered:** a release or delivery snapshot contains current supporting evidence.

A completed task checkbox is not proof of testing or delivery. Test evidence becomes stale when a material linked requirement or implementation changes after the recorded result.

## Confirmed, derived, and suggested links

- **Confirmed links** are explicitly accepted into `.tie/rtm.yaml`.
- **Derived links** come from deterministic configured evidence such as a known test report.
- **Suggested links** may come from Git or an agent and remain non-authoritative until reviewed.

Suggested links never increase official coverage on their own.

## Baselines and scope movement

Named baselines snapshot approved requirement scope. The RTM can then show additions, changes, removals, waivers, and work that entered without an approved requirement. Baselines are lightweight scope controls, not a replacement for Git history or an external test-management system.
